A profiler for coding agents · Claude Code, Codex, Pi

See what your coding agents load, what it costs, and where they go wrong.

Quench reads the session history your agents already keep on this machine. One command shows what every session starts with, how that context grows, which models and effort levels you really use, and which tool calls keep failing the same way. Nothing leaves your machine unless you opt in.

gh release download --repo JarenKempton/quench --pattern "quench-linux-x64" --output ~/.local/bin/quench

Linux and macOS, x64 and arm64. chmod +x, then run quench with no arguments. MIT.

What it costs

Most of what the model reads is the same thing, again and again.

Every model call re-reads the whole context. So the instructions, skill listings and MCP definitions a session starts with are paid for on every call that follows. Quench calls that the starting load: the context the first model call carried, and its share of all the tokens a harness processed.

Numbers you can trace

  • Starting load is the context at a session's first model call. The share in parentheses is how much of everything processed was that same load, re-read.
  • Peak context is the largest single call. Compactions are counted from the harness's own record, with the tokens they replaced.
  • Unknown stays unknown. Codex records no tool error flag, so Quench says "errors not recorded" rather than zero. Effort a harness did not log is "unknown".
  • Every value traces to a line in a file on disk. Lines that no longer fit a harness's format are counted as unparsed and shown, so a format change is visible instead of silently wrong.

Where they go wrong

The same tool call failing the same way, eleven times, in six sessions.

Agents repeat mistakes across sessions because nothing connects them. Quench groups tool failures by what failed: the same missing file, the same missing command, the same rejection by a hook, the same bad input. Each row shows how often, in how many sessions, the longest streak in a row, and how much error output it pushed into context.

Then read the session that went wrong

quench runs lays one session out as what you asked, what the agent did, and what you said back. A run is everything between two of your messages: model, effort, context at start and peak, tool calls and errors, subagents, compactions, duration.

Your reply is the outcome signal. "no, use the existing router" after a run is worth more than any benchmark, and it is already on your disk.

Eight commands

Offline by default. Model calls only where it says so.

  • quench

    A short summary: what sessions start with, what is worth a look, busiest projects.

  • quench profile [section]

    Every table, or one: projects, mcp, instructions, skills, failures.

  • quench report

    Per harness: starting load, peak context, compactions, tool errors, models and effort.

  • quench runs [session]

    One session as prompt → what the agent did → your reply. Default: the latest one here.

  • quench sources [session]

    What one session read and loaded: native reads, shell reads, injected instructions, MCP calls.

  • quench steering <dir>

    Current instruction-file inventory for a project and the rule candidates inside them.

  • quench worktrees

    Idle linked worktrees, which are safe to remove and why the rest are kept. Read-only.

  • quench corrections

    Human correction and agent supervision rates, counted separately. Opt-in: asks a model with your own key, and --dry-run shows what would be sent first.

Every command takes --json. Agents ask Quench through a skill that runs quench … --json, not an MCP server, because MCP tool definitions are the largest source of context bloat Quench measures.

How it is built

Rules the code follows.

Local-first
Everything works offline from files already on the machine. Anything that sends data anywhere is opt-in and says exactly what it sends.
No fake numbers
Every number traces to a file on disk. Estimates are labeled. If a harness did not record something, the field is null, never zero.
Not an orchestrator
Quench reads what agents did and helps you steer them. It never runs an agent, and it never removes a worktree.
Recorded loads over predictions
When a session's history records the instructions it loaded, that is what gets reported, compared with disk only by exact hash.
Bring your own compute
Model-backed analysis uses your key. A verdict is cached and paid for once. Running Quench costs its maintainers nothing per user.
Streams at scale
Sessions are read one at a time, line by line. On the reference machine, 3.6 GB across 1,220 files reads in about 8 s with a 0.5 GB peak.
